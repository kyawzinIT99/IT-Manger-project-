A. Architecture Diagram

Target-state design on Google Cloud Platform — asia-east2 (Hong Kong). All components are fully managed or serverless. No VMs, no OS patching, no server management.

B. Design Rationale

Why Google Cloud Platform?

Decision FactorGCP Advantage
Hong Kong data residencyasia-east2 is a full GCP region in Hong Kong — PII never leaves the jurisdiction
No servers to manageCloud Run is fully serverless: no VMs, no OS patching, no capacity planning

Small team friendlyFewer moving parts than EKS/ECS; managed DB eliminates DBA burden
Regional expansionIdentical Terraform modules deploy to asia-southeast1 (SG) and asia-east1 (TW)
Budget fitPay-per-use compute + committed-use DB discounts keep steady state at 41% of budget

How we meet 99.9% availability

  1. Multi-zone Cloud Run — instances in at least two availability zones. If one zone fails, the LB routes to surviving instances automatically.
  2. Cloud SQL HA — synchronous replication to a standby in a different zone. Automatic failover in < 60 seconds.
  3. Cloud CDN — cached product pages and media continue serving even if compute is briefly degraded.
  4. Health checks — Global LB runs checks every 10s. Unhealthy instances drained within 30s.
Where it can still fail: A full regional outage of asia-east2 (extremely rare). Mitigation: CDN continues serving cached pages; cross-region DR is a Phase 2 item. A bad deployment is mitigated by blue-green traffic splitting + instant rollback.

How the database survives losing a node (RPO ≤ 15 min)

Protection LayerRPO AchievedHow
HA synchronous replication0 minutesStandby has every committed transaction. Auto-failover promotes standby
Automated backups (PITR)≤ 15 minPoint-in-time recovery via binary log. Recover to any second in retention window
Cross-region backup≤ 24 hoursDaily export to Cloud Storage in asia-southeast1 (Singapore). Regional disaster protection

How the 10× campaign spike is absorbed

  • Cloud Run auto-scaling responds to concurrent request count. From 2 to 20 instances takes ~15–30 seconds.
  • Configuration: max-instances=50 (hard cost cap), concurrency=80 (PHP-FPM per container).
  • Read replica added to Cloud SQL during campaign window to offload catalogue queries (scheduled via Terraform toggle).
  • CDN warm-up — pre-cache product pages before each campaign, reducing origin load by ~70%.

D. Automation

D1. Infrastructure-as-Code Excerpt — Cloud Run Service (Terraform)

# Cloud Run Service — Northpoint Living PHP E-commerce

resource "google_cloud_run_v2_service" "storefront" {
  name     = "northpoint-storefront"
  location = var.region   # "asia-east2"
  ingress  = "INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER"

  template {
    scaling {
      min_instance_count = var.min_instances   # 2 for HA
      max_instance_count = var.max_instances   # 50 hard cap
    }

    vpc_access {
      connector = google_vpc_access_connector.main.id
      egress    = "PRIVATE_RANGES_ONLY"
    }

    containers {
      image = "${var.region}-docker.pkg.dev/${var.project_id}/northpoint/storefront:${var.image_tag}"
      ports { container_port = 8080 }

      resources {
        limits = { cpu = "2", memory = "4Gi" }
        cpu_idle = false   # Always-allocated for e-commerce latency
      }

      env { name = "DB_HOST"; value = google_sql_database_instance.primary.private_ip_address }
      env { name = "MEDIA_BUCKET"; value = google_storage_bucket.product_media.name }

      # Secrets from Secret Manager (never hardcoded)
      env {
        name = "DB_PASSWORD"
        value_source {
          secret_key_ref {
            secret  = google_secret_manager_secret.db_password.secret_id
            version = "latest"
          }
        }
      }

      startup_probe {
        http_get { path = "/api/health" }
        initial_delay_seconds = 5
        failure_threshold     = 10
      }
      liveness_probe {
        http_get { path = "/api/health" }
        period_seconds = 30
      }
    }
  }

  traffic {
    type    = "TRAFFIC_TARGET_ALLOCATION_TYPE_LATEST"
    percent = 100
  }
}

F. Risk Register — Top 5 Risks

#RiskLikelihoodImpactMitigation
1 Campaign spike exceeds 10× estimate Medium High Set max_instances=50. Pre-provision read replica. Load-test at 15× before each campaign. Cloud Armor rate-limits bot traffic.
2 Data breach / PDPO non-compliance Low Critical All data in asia-east2 (HK). AES-256 at rest, TLS in transit. VPC Service Controls. Access logging. Annual PDPO review.
3 Bad deployment breaks production Medium High Blue-green deploy: new revision gets 0% traffic until smoke test passes. Instant rollback via gcloud CLI. Canary → full rollout.
4 Cloud SQL failover exceeds 60s Low Medium RTO target is 60 min, not 60 sec. Even 5-min failover is well within RTO. Cloud Run retries automatically. CDN serves cached pages.
5 Agency key-person risk (Visible One) Medium High All infra in Terraform (reproducible). Runbooks in shared wiki. CI/CD = no deep knowledge for deploys. Cross-train ≥1 engineer within 60 days.
Risk #5 is an agency risk to Visible One, not only a client risk. If platform knowledge lives in one person's head, the agency's ability to service this client — and its credibility — is at stake. IaC and documentation are the mitigation.
